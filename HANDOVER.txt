Parrot / echo service
---------------------
- HBlink4 has an in-process local DMR parrot service based on the classic HBlink3 playback behaviour without running a second legacy HBLink daemon.
- hblink4/parrot.py records accepted local group-voice DMRD frames and replays the original packet sequence only to the originating repeater/hotspot after a proper voice terminator.
- Production uses TG9990, a 2-second delay, 60-ms packet cadence and a 120-second recording cap.
- TG9990 is intentionally absent from ordinary routed TG lists. The parrot receives an empty normal route cache and is never fanned out to another local repeater, HomeBrew outbound or OpenBridge trunk.
- A numerically identical TG received from an external trunk does not invoke the local parrot.
- Playback is cancelled if the originating repeater disconnects or reuses the slot before/during echo.
- Calls that exceed the configured recording cap or end through timeout/fast-terminator handling are discarded instead of replayed incompletely.
- Parrot lifecycle payloads contain the originating DMR timeslot. The dashboard reports it explicitly as TS1 or TS2 throughout recording/playback activity.

Upstream observations to track
------------------------------
- Dashboard release/version ownership is split between server.py and the composed admin_app entry point. Direct use of dashboard.server can therefore diverge from the deployed composed application's version. A single version source would avoid stale reporting.
- Browser WebSocket ownership is embedded in dashboard.html rather than exposed through a shared event-dispatch module. Extension helpers can otherwise create duplicate WebSocket connections or silently diverge from the main dashboard feed.
- Informational UI failures were previously silent: a failed secondary activity socket could leave a healthy-looking Ready state. A stale/disconnected activity indicator or shared client-side event bus would improve observability.
- The original parrot dashboard regression test asserted source-code strings rather than exercising the event path, which was insufficient to catch the production symptom. Runtime/browser-level event-state testing would improve coverage.
- hblink4/events.py uses non-blocking stream sockets with framed messages and `sendall`; an output buffer/async writer would be safer against partial/non-blocking sends and dashboard telemetry frame loss or corruption under backpressure.
- The non-blocking TCP EventEmitter connect path should explicitly complete/check an in-progress connection before treating it as usable; the local Unix-socket production path does not depend on that TCP edge case.
- Existing FastAPI `on_event` deprecation warnings remain technical debt; migrate startup/shutdown handling to lifespan when convenient.
- None of these observations currently indicate a discovered DMR routing/parrot RF-core defect; the RF echo path remained functional during the dashboard failure.

Safety notes
------------
- Never expose HomeBrew passphrases, full configuration backups, password hashes, Cognito tokens/credentials, WebAuthn private material or other secrets in logs/repository/public APIs.
- Never run both blue and green HBlink4 cores simultaneously when duplicate HomeBrew/OpenBridge sessions are possible.
- Treat the live EIP association as the authoritative production color.
- Keep external network TGs and local service TGs explicitly isolated; the parrot must never become a transit/bridge path.
