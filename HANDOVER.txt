Parrot / echo service
---------------------
- HBlink4 has an in-process local DMR parrot service based on the classic HBlink3 playback behaviour without running a second legacy HBLink daemon.
- hblink4/parrot.py records accepted local group-voice DMRD frames and replays the original packet sequence only to the originating repeater/hotspot after a proper voice terminator.
- Production uses TG9990, a 2-second delay, 60-ms packet cadence and a 120-second recording cap.
- TG9990 is intentionally absent from ordinary routed TG lists. The parrot receives an empty normal route cache and is never fanned out to another local repeater, HomeBrew outbound, or OpenBridge trunk.
- A numerically identical TG received from an external trunk does not invoke the local parrot.
- Playback is cancelled if the originating repeater disconnects or reuses the slot before/during echo.
- Calls that exceed the configured recording cap or end through timeout/fast-terminator handling are discarded instead of replayed incompletely.
- Lifecycle payloads include the originating DMR timeslot, so the dashboard can report TS1 or TS2 throughout recording/playback.

Current dashboard defect and fix
--------------------------------
- After PR #10/website PR #26 production deployment, RF parrot operation still worked but Local DMR Services stayed at Ready during a live parrot session.
- The helper had created an independent second `/ws` WebSocket and silently ignored any problem on that informational path. The main dashboard WebSocket continued to operate, leaving no visible error while the local-service card remained stale.
- Branch fix/parrot-dashboard-live-events-version changes the public helper to subscribe to the already-established main dashboard WebSocket; the administrator page retains a standalone `/ws` fallback because it has no main dashboard socket.
- Normal stream event fields are normalised (`rf_src` -> `src_id`, `packets` -> `packet_count`) so the fallback path shows the same radio and packet metadata as parrot-specific lifecycle events.
- Timeslot remains explicit in the activity identity line as TS1/TS2 and is preserved through playback/completion lifecycle payloads.
- The previous focused UI test only checked that lifecycle strings existed in JavaScript. Coverage now also verifies dashboard receiver passthrough of parrot events, shared-socket subscription, field normalisation and release/version wiring.
- The visible dashboard version had remained hard-coded at 1.2.0 through the parrot feature rollout. The composed deployed application now publishes v1.3.0 and uses cache-buster `20260830-parrot-live-2`.
