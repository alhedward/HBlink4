Production incident: parrot attenuation validator mismatch
---------------------------------------------------------
- Production core entered a systemd restart loop after the admin/API persisted parrot.voice_telemetry_attenuation_db=60.0.
- The admin/API intentionally accepts attenuation values from 0 through 60 dB and displays 60.0 as -60 dB relative voice-report level.
- hblink4/parrot_voice.py on production revision f97d74c40902032bdb2258339c13c50227bb3f93 still enforced a 30 dB runtime ceiling, so the next core startup rejected an otherwise valid admin-written configuration.
- Emergency recovery temporarily set the live attenuation back to 6.0 dB; HBlink4 then accepted hotspot connections again and TG9990 DMR-to-DMR parrot operation was confirmed working.
- fix/parrot-runtime-60db raises only the runtime ceiling to 60 dB and adds focused regression coverage so runtime and admin validation remain aligned.
- Do not restore an operator-selected value above 30 dB in production until the runtime fix is merged, pinned by hblink-website and deployed through normal CI/CD.

New RF capture findings: 49-bit root cause confirmed
----------------------------------------------------
- hblink9990-voice.pcap contains a clean inbound TG9990 call, its byte-identical parrot echo, and the full deterministic telemetry stream.
- Capture split: 86 inbound DMRD packets, 86 byte-identical echo packets, then 237 telemetry packets.
- Telemetry contains three voice headers, 233 voice bursts (699 AMBE frames), and one terminator.
- The leading/trailing telemetry silence frames match the known DMR silence pattern.
- DMR framing/interleave remains proven good; the defect is inside the 49 AMBE voice parameter bits.
- Pinned OpenDMR opendmr.cpp serializes b[0..8] sequentially with widths 7,5,5,9,7,5,4,4,3.
- OpenDMR's own OP25-derived MBEEncoder encode_49bit() uses a different mapping and scatters low-order bits through positions 35..48.
- Captured telemetry interpreted with the sequential wrapper layout recovers sane encoder parameters; interpreted as encode_49bit() data, roughly half the frames produce impossible b[1] values greater than 16.
- Recovering b[0..8] from the sequential layout and repacking with encode_49bit() restores valid encoder parameter semantics without re-vocoding.
- Production-derived regression vector:
    legacy canonical:   b40930d10843ce4769
    recovered b[]:      [90, 0, 6, 87, 78, 8, 14, 13, 1]
    corrected canonical:b0357c6213d29f05c5
    corrected DMR AMBE: d5ee220741b9680b2f
